## 1. Purpose and scope

This SRS defines verifiable functional and non-functional requirements for the Tooang backend. It covers authentication, multi-role authorization, user administration, place and menu management, reviews, carts, orders, verification links, auditing, persistence, and operations.

Requirements use stable identifiers. The terms **shall**, **should**, and **may** indicate mandatory, recommended, and optional behavior respectively.

## 2. System context

Tooang Backend is a NestJS modular monolith that exposes a JSON REST API to a web frontend and persists data in PostgreSQL through Prisma.

```text
Web client
   |
   | HTTPS + JSON REST
   v
NestJS API (/api/v1)
   |
   | Prisma
   v
PostgreSQL
```

The request path inside a feature follows:

```text
Controller -> Service -> Repository -> Prisma -> PostgreSQL
```

Architectural constraints and module boundaries are defined in [`../ARCHITECTURE.md`](../ARCHITECTURE.md).

## 3. Technology and implementation constraints

- SRS-CON-001: The application shall use TypeScript and NestJS 11.
- SRS-CON-002: PostgreSQL shall be the authoritative relational datastore.
- SRS-CON-003: Prisma 7 shall manage database access and migrations.
- SRS-CON-004: Zod shall validate request params, queries, and bodies.
- SRS-CON-005: The externally supported API shall be rooted at `/api/v1`.
- SRS-CON-006: The backend shall remain deployable as one modular-monolith process.
- SRS-CON-007: Monetary values shall use PostgreSQL decimal types and `Prisma.Decimal`, never JavaScript floating-point arithmetic.
- SRS-CON-008: Feature modules shall use the minimum controller, service, repository, schema, and module structure unless additional files have a specific responsibility.

## 4. Actors and authorization model

| Actor | Authentication | Effective access |
| --- | --- | --- |
| Visitor | None | Published places, available menus, visible reviews, and the minimal public order-verification response |
| USER | Access token | Own profile, verified-purchase reviews, carts, and orders |
| CASHIER | Access token plus place assignment | Read and process orders only for assigned places |
| OWNER | Access token plus ownership lookup | USER access plus assigned place data and order processing |
| ADMIN | Access token plus current role verification | Platform operations across places, menus, reviews, users, and orders, excluding role/security administration reserved for SUPER_ADMIN |
| SUPER_ADMIN | Access token plus current role verification for sensitive operations | System-wide administration, role/security administration, and moderation |

- SRS-RBAC-001: The system shall support multiple roles per user through `UserRole`.
- SRS-RBAC-002: Every active user shall have at least one role.
- SRS-RBAC-003: Endpoint-level role checks shall not replace resource-level ownership checks.
- SRS-RBAC-004: OWNER mutations shall verify a `PlaceOwner` association between the authenticated internal `User.id` and target `Place.id`.
- SRS-RBAC-005: OWNER queries shall filter ownership in the database and shall not filter an unrestricted result set in memory.
- SRS-RBAC-006: A resource belonging to a different OWNER shall be returned as not found to prevent tenant enumeration.
- SRS-RBAC-007: ADMIN and SUPER_ADMIN may bypass place ownership checks for approved platform-operations workflows but shall remain subject to validation and auditing.
- SRS-RBAC-008: Only SUPER_ADMIN shall assign or revoke roles.
- SRS-RBAC-009: The last role of an active user shall not be revoked.
- SRS-RBAC-010: `OWNER` shall not be revoked while the user has a `PlaceOwner` assignment.
- SRS-RBAC-011: `ADMIN` is the Platform Operations Administrator role. It may perform explicitly allowlisted system-wide user-support, place, menu, review-moderation, and order-operations workflows, but shall not assign or revoke roles, manage authentication secrets, or inherit any other SUPER_ADMIN-only permission.
- SRS-RBAC-012: The system shall support the `CASHIER` role and a persisted assignment between a cashier and each place at which the cashier may operate.
- SRS-RBAC-013: CASHIER access shall be scoped by `placeId`; queries shall filter assigned places in the database, and mutations shall verify the assignment before changing an order.
- SRS-RBAC-014: CASHIER shall not receive OWNER place-configuration, menu-management, user-administration, or cross-place permissions.

## 5. Functional requirements

### 5.1 Authentication and refresh sessions

- SRS-AUTH-001: Registration shall accept a full name, email, and password that pass the configured validation policy.
- SRS-AUTH-002: Email shall be normalized before uniqueness checking and storage.
- SRS-AUTH-003: Registration shall create the user and initial `USER` role in one database transaction.
- SRS-AUTH-004: Passwords shall be stored only as adaptive password hashes.
- SRS-AUTH-005: Login shall reject invalid credentials without revealing whether an email exists.
- SRS-AUTH-006: Login shall return or deliver a short-lived access token and establish a refresh session.
- SRS-AUTH-007: Raw refresh tokens shall not be stored; only a cryptographic token hash shall be persisted.
- SRS-AUTH-008: Refresh shall rotate the token by revoking/replacing the current session and creating its replacement atomically.
- SRS-AUTH-009: Refresh-session replacement shall maintain `familyId`, `replacedById`, expiry, revocation, and creation data consistent with the Prisma model.
- SRS-AUTH-010: Reuse of a revoked/replaced refresh token shall cause the affected token family to be revoked according to the authentication policy.
- SRS-AUTH-011: Logout shall revoke the submitted refresh session or the applicable token family.
- SRS-AUTH-012: Expired, revoked, malformed, or unknown refresh tokens shall be rejected.
- SRS-AUTH-013: Soft-deleted users shall not log in, refresh, or access protected resources.
- SRS-AUTH-014: Authentication responses shall never expose `passwordHash`, refresh-token hashes, or internal session relationships.
- SRS-AUTH-015: Passwords shall contain 8 through 128 characters. No mandatory mixture of uppercase letters, lowercase letters, numbers, or symbols shall be imposed.
- SRS-AUTH-016: Registration and password changes shall reject passwords found in the configured known/common-password denylist.
- SRS-AUTH-017: Passwords shall be hashed with bcrypt using an approved, configurable work factor before storage. The implementation shall ensure every byte of an accepted password affects the hash, using a documented safe pre-hashing construction or a stricter byte-length rejection where required by the bcrypt implementation.
- SRS-AUTH-018: Access tokens shall expire 15 minutes after issuance.
- SRS-AUTH-019: Standard refresh sessions shall expire 30 days after issuance. When the user explicitly selects the optional remember-me mode, the refresh session may expire after 90 days.
- SRS-AUTH-020: A refresh token delivered by cookie shall use `HttpOnly`, `SameSite=Lax`, and `Path=/auth/refresh`; it shall use `Secure=true` and HTTPS only in production, and may use `Secure=false` on localhost in development.
- SRS-AUTH-021: Authentication attempts shall use progressive rate limiting. The baseline login limit shall be 10 attempts per 15 minutes per source IP, with increasingly restrictive throttling for repeated abuse and no permanent account lockout caused solely by failed attempts.

### 5.2 User and role management

- SRS-USR-001: An authenticated user shall retrieve their active profile using the `/me` resource.
- SRS-USR-002: An authenticated user shall update only supported fields of their own profile.
- SRS-USR-003: ADMIN and SUPER_ADMIN shall list and retrieve active users with bounded pagination for platform-support workflows.
- SRS-USR-004: SUPER_ADMIN shall assign a system role that exists in the `Role` table.
- SRS-USR-005: Role assignment shall be idempotent or return a deterministic conflict response.
- SRS-USR-006: SUPER_ADMIN shall revoke a role only when minimum-role and OWNER invariants remain valid.
- SRS-USR-007: ADMIN and SUPER_ADMIN may deactivate a user; deactivation shall set `deletedAt` and revoke active refresh sessions atomically.
- SRS-USR-008: System roles shall be seeded and shall not be deleted through general user endpoints.

### 5.3 Place management

- SRS-PLC-001: Public list and detail operations shall return only places with `isPublished = true` and `deletedAt = null`.
- SRS-PLC-002: The public place list shall support bounded pagination and documented filters.
- SRS-PLC-003: Public place detail shall be addressable by unique slug.
- SRS-PLC-004: Place data shall support type, name, description, address, city, coordinates, contact data, logo, cover image, business hours, and ordering state as modeled in Prisma.
- SRS-PLC-005: Place type shall be one of `RESTAURANT`, `CAFE`, `FOOD_STALL`, or `OTHER`.
- SRS-PLC-006: Place creation and initial owner assignment shall be atomic.
- SRS-PLC-007: An assigned owner shall have the `OWNER` role.
- SRS-PLC-008: An active place shall retain at least one owner unless an explicitly logged SUPER_ADMIN exception is supported.
- SRS-PLC-009: A slug shall be normalized, unique, and shall not match a reserved API or frontend route.
- SRS-PLC-010: A place shall be publishable only after required identity fields, at least one owner, and the configured minimum menu content exist.
- SRS-PLC-011: Ordering shall be enabled only for an active, published place with at least one available menu item.
- SRS-PLC-012: Disabling ordering shall block new checkouts and shall not cancel existing orders.
- SRS-PLC-013: Soft deletion shall disable publishing and ordering and shall be blocked while unresolved orders violate the retention policy.
- SRS-PLC-014: Every place shall store a valid IANA timezone identifier, such as `Asia/Jakarta`, `Asia/Tokyo`, or `Asia/Singapore`.
- SRS-PLC-015: ADMIN may perform the OWNER place-management operations across places as a platform-operations workflow; those mutations shall be audited.

### 5.4 Business hours

- SRS-HRS-001: A place shall store no more than one business-hour record for each day of the week.
- SRS-HRS-002: A closed day shall have `isClosed = true` and null opening/closing times.
- SRS-HRS-003: An open day shall provide non-equal opening and closing times.
- SRS-HRS-004: Overnight hours shall be evaluated as closing on the following calendar day.
- SRS-HRS-005: Opening-state calculations shall use `Place.timezone` and shall not trust the server default or client timezone.
- SRS-HRS-006: Database timestamps shall be stored in UTC and converted to `Place.timezone` when producing place-local dates and times for display or business-rule evaluation.

### 5.5 Categories and menu items

- SRS-MNU-001: Public menu queries shall return only non-deleted, available items in active categories belonging to a published place.
- SRS-MNU-002: Public menu queries shall support filtering by place, `FOOD`/`DRINK`, and category.
- SRS-MNU-003: OWNER shall create, update, order, enable/disable, and soft-delete categories/items only within assigned places.
- SRS-MNU-004: `MenuCategory.placeId` and `MenuItem.placeId` shall match for every menu item.
- SRS-MNU-005: Category names shall be normalized and unique case-insensitively within a place.
- SRS-MNU-006: Menu prices shall be non-negative decimals with the supported precision.
- SRS-MNU-007: `sortOrder` shall be a non-negative integer.
- SRS-MNU-008: Deleted or unavailable menu items and items in inactive categories shall not enter a cart or order.
- SRS-MNU-009: A menu update shall not modify existing `OrderItem` snapshot values.
- SRS-MNU-010: Soft-deleting a menu item shall preserve order history and shall cause matching active cart items to be removed or reported invalid on cart retrieval.
- SRS-MNU-011: A menu name shall contain 1 through 120 characters, and a menu description shall contain no more than 1,000 characters.
- SRS-MNU-012: ADMIN may perform OWNER category and menu operations across places as a platform-operations workflow; those mutations shall be audited.

### 5.6 Reviews

- SRS-REV-001: An authenticated active user may create a review only for an order owned by that user whose status is `COMPLETED`.
- SRS-REV-002: A rating shall be an integer from 1 through 5.
- SRS-REV-003: Users shall update and soft-delete only their own reviews.
- SRS-REV-004: A completed order shall have at most one stored review. Re-submitting a soft-deleted review for that order shall restore and update the existing row instead of creating a conflicting row.
- SRS-REV-005: ADMIN and SUPER_ADMIN shall moderate any review, and the action shall be audited.
- SRS-REV-006: Public review queries and rating summaries shall exclude soft-deleted reviews.
- SRS-REV-007: A review shall reference the qualifying completed order and its place; a menu-item review shall additionally target an item included in that order's item snapshots.
- SRS-REV-008: Different completed orders may each receive a review, including when they belong to the same place or include the same menu item.
- SRS-REV-009: Review text shall contain no more than 2,000 characters.

### 5.7 Carts

- SRS-CART-001: A user shall maintain at most one cart for each place.
- SRS-CART-002: Users shall access only their own carts.
- SRS-CART-003: Every cart item shall reference a menu item whose `placeId` matches the cart's `placeId`.
- SRS-CART-004: Quantity shall be a positive integer within the configured maximum.
- SRS-CART-005: Adding an existing menu item shall update its quantity rather than create a duplicate cart row.
- SRS-CART-006: Setting quantity to zero shall remove the item.
- SRS-CART-007: Cart item notes shall be length-limited and safely rendered by consumers.
- SRS-CART-008: Cart retrieval shall return current server-side prices and shall identify or remove no-longer-orderable items.
- SRS-CART-009: A cart may be retained while ordering is disabled, but it shall not be checked out.
- SRS-CART-010: A cart shall contain no more than 50 distinct menu items.
- SRS-CART-011: Quantity shall not exceed 99 for any one cart item, and the sum of quantities across the cart shall not exceed 200.

### 5.8 Checkout and order creation

- SRS-ORD-001: Checkout shall require an authenticated active user and a non-empty cart owned by that user.
- SRS-ORD-002: Checkout shall re-read the place, category, menu availability, and prices inside the transaction.
- SRS-ORD-003: Checkout shall reject a deleted, unpublished, or ordering-disabled place.
- SRS-ORD-004: Checkout shall reject any cross-place, deleted, unavailable, inactive-category, or invalid-quantity item.
- SRS-ORD-005: The server shall calculate `unitPrice`, `lineTotal`, and `subtotal` using decimal arithmetic.
- SRS-ORD-006: `lineTotal` shall equal `unitPrice * quantity`, and `subtotal` shall equal the sum of line totals.
- SRS-ORD-007: Order creation shall snapshot `itemName`, `itemType`, `unitPrice`, quantity, note, and line total.
- SRS-ORD-008: Order creation shall generate a unique human-readable `orderCode` and unique opaque `verificationToken`.
- SRS-ORD-009: The order, all items, expiry time, and cart clearing shall be committed atomically.
- SRS-ORD-010: Checkout shall accept an idempotency key scoped to the authenticated user and checkout operation.
- SRS-ORD-011: Retrying a completed request with the same idempotency key and equivalent input shall return the original result without creating another order.
- SRS-ORD-012: Reusing an idempotency key with different input shall return a conflict.
- SRS-ORD-013: DINE_IN shall validate table information according to place policy; TAKEAWAY shall not retain an irrelevant table number.
- SRS-ORD-014: The backend shall not create payment records or report an order as paid.
- SRS-ORD-015: Customer name shall contain 1 through 100 characters, and order notes shall contain no more than 500 characters.
- SRS-ORD-016: A new `PENDING` order shall set `expiresAt` to 15 minutes after creation.
- SRS-ORD-017: Checkout idempotency shall be persisted in a dedicated `idempotency_keys` table containing at least `id`, `key`, `user_id`, `endpoint`, `request_hash`, `response_status`, `response_body`, `created_at`, and `expires_at`.
- SRS-ORD-018: An idempotency record shall be scoped by authenticated user and endpoint. The same key and equivalent request hash shall return the stored response; the same key with a different request hash shall return HTTP `409 Conflict`.
- SRS-ORD-019: Checkout idempotency records shall expire 24 hours after creation.

The dedicated idempotency persistence required by SRS-ORD-017 is not represented in the current Prisma schema and therefore requires a schema migration before checkout idempotency is implemented.

### 5.9 Order retrieval, verification, and lifecycle

- SRS-STS-001: A user shall list and retrieve only their own orders.
- SRS-STS-002: OWNER shall list, retrieve, and process only orders associated with assigned places.
- SRS-STS-003: ADMIN and SUPER_ADMIN shall retrieve and process all orders subject to audit requirements.
- SRS-STS-004: New orders shall start in `PENDING`.
- SRS-STS-005: Status transitions shall be limited to:

```text
PENDING   -> CONFIRMED | CANCELLED | EXPIRED
CONFIRMED -> PREPARING | CANCELLED
PREPARING -> READY | CANCELLED
READY     -> COMPLETED | CANCELLED
COMPLETED -> terminal
CANCELLED -> terminal
EXPIRED   -> terminal
```

- SRS-STS-006: Status mutation shall condition the database update on the expected previous status to prevent races.
- SRS-STS-007: `confirmedAt`, `completedAt`, and `cancelledAt` shall be set only when the corresponding transition occurs.
- SRS-STS-008: A user may cancel their own `PENDING` order; broader cancellation requires an explicit policy.
- SRS-STS-009: An idempotent scheduled job shall move expired `PENDING` orders to `EXPIRED`.
- SRS-STS-010: Terminal order transactional data shall be immutable.
- SRS-STS-011: Human order-code lookup shall be rate-limited and shall not grant mutation authority.
- SRS-STS-012: QR/link data shall use the opaque verification token and shall not embed database IDs or personal information.
- SRS-STS-013: A valid public verification token shall return only `orderCode`, place display name, order status, fulfillment type, creation time, expiry time, and the timestamp corresponding to the current terminal or processing state. It shall not disclose customer identity/contact data, table number, order items, notes, prices, internal IDs, or any token.
- SRS-STS-014: A cashier shall have an authenticated CASHIER, OWNER, ADMIN, or SUPER_ADMIN session authorized for the order's place before retrieving operational detail or changing status.
- SRS-STS-015: Public verification shall be read-only. Operational details and order mutations shall use an authenticated endpoint and shall re-check place-scoped authorization.
- SRS-STS-016: A public verification token shall be unguessable, shall not appear in logs or response bodies, and shall cease to be publicly usable 30 days after the order enters a terminal state. An expired, unknown, or disabled token shall return the same non-disclosing not-found response.

### 5.10 Audit logging

- SRS-AUD-001: The system shall audit role changes, OWNER and CASHIER place assignments, ordering-setting changes, ADMIN cross-place mutations, review moderation, user deactivation, and order-status changes.
- SRS-AUD-002: Each audit record shall identify actor, action, target type, target ID, timestamp, and safe before/after data where applicable.
- SRS-AUD-003: Audit data shall never include passwords, raw access/refresh tokens, token hashes, verification tokens, secrets, or unnecessary personal data.
- SRS-AUD-004: An auditable state mutation and its required audit record shall be committed atomically when feasible.
- SRS-AUD-005: Audit records shall be append-only to ordinary application users.

## 6. Data requirements

- SRS-DATA-001: Internal foreign keys shall use `User.id`; public APIs may expose `User.userId` where required.
- SRS-DATA-002: UUID defaults in Prisma shall be used for internal entity identifiers unless a requirement states otherwise.
- SRS-DATA-003: Active-data queries shall exclude records with non-null `deletedAt`.
- SRS-DATA-004: Soft-deleted users, places, menus, and reviews shall follow the restore/conflict rules in `application-rules.md`.
- SRS-DATA-005: Hard deletion shall not break retained order and audit history.
- SRS-DATA-006: Order item snapshots shall remain readable when the source menu item is later deleted.
- SRS-DATA-007: Database migrations should add check constraints for rating range, non-negative monetary fields and sort order, positive quantities, and business-hour consistency.
- SRS-DATA-008: Application validation shall remain mandatory even when a database check constraint exists.
- SRS-DATA-009: Production migrations shall be applied using `prisma migrate deploy` and shall not use destructive development migration commands.
- SRS-DATA-010: Backup, restore, retention, and anonymization procedures shall be implemented and tested before production launch.
- SRS-DATA-011: The schema shall support `Place.timezone`, the `CASHIER` role with place-scoped cashier assignments, a unique review-to-order relationship, and the dedicated checkout idempotency records required by this SRS.
- SRS-DATA-012: Retention periods shall be measured from record creation unless a requirement specifies another event.

| Data | Retention |
| --- | ---: |
| Access/session logs | 90 days |
| Authentication sessions | Session expiry plus 30 days |
| Audit logs | 1 year |
| Order records | 5 years |
| Payment transaction metadata, if introduced | 5 years |
| Idempotency records | 24 hours |
| Email verification tokens | No more than 30 days |
| Password reset tokens | 24 hours |
| Deleted-account personal data | 30 days |
| Anonymous analytics | 1 year |

- SRS-DATA-013: Account deletion shall revoke active sessions and anonymize or remove the account's personal data within 30 days, while legally or operationally retained transaction records remain intact.
- SRS-DATA-014: Anonymized retained orders shall replace the customer name with `Deleted User`, clear phone and email values, and preserve non-personal transaction fields such as order totals, order items, and transaction metadata.
- SRS-DATA-015: Retention deletion/anonymization jobs shall be idempotent, auditable, and designed so that backups age out affected data according to the documented backup lifecycle.

## 7. API and interface requirements

- SRS-API-001: The API shall exchange UTF-8 JSON except for explicitly documented media endpoints.
- SRS-API-002: Protected endpoints shall accept an access token through `Authorization: Bearer <token>`.
- SRS-API-003: Request validation failures shall return a consistent machine-readable error structure.
- SRS-API-004: List endpoints shall implement pagination and enforce a maximum page size.
- SRS-API-005: Resource routes shall use plural nouns and kebab-case.
- SRS-API-006: User-owned resources should use `/me`; OWNER-managed resources shall be scoped by `placeId`.
- SRS-API-007: `400` shall represent invalid input, `401` invalid authentication, `403` global role denial, `404` absent/hidden/foreign-tenant resources, and `409` state or uniqueness conflicts.
- SRS-API-008: Raw Prisma errors and stack traces shall not be returned to clients.
- SRS-API-009: API contracts shall be documented under `docs/api-specification` and updated with implementation changes.
- SRS-API-010: Backward-incompatible public contract changes shall use a new API version or an approved migration period.

## 8. Security and privacy requirements

- SRS-SEC-001: Production traffic shall use HTTPS at the deployment boundary.
- SRS-SEC-002: Access-token and refresh-token signing secrets shall be distinct, sufficiently random, and stored outside source control.
- SRS-SEC-003: Logs shall redact authorization headers, cookies carrying tokens, raw tokens, password fields, and order verification tokens.
- SRS-SEC-004: Authentication, refresh, human-code lookup, and verification endpoints shall be rate-limited.
- SRS-SEC-005: Database queries shall use Prisma parameterization and shall not concatenate untrusted SQL.
- SRS-SEC-006: Response selection shall exclude password hashes, token hashes, replacement-session internals, and private audit content.
- SRS-SEC-007: Input length limits shall be enforced server-side, including the explicit customer-name, menu, order-note, and review limits in this SRS; other accepted text fields shall have documented bounds before their endpoints are released.
- SRS-SEC-008: Uploaded or externally referenced image URLs shall be validated according to an approved media policy before media features launch.
- SRS-SEC-009: CORS origins and cookie attributes shall be environment-specific and restrictive in production.
- SRS-SEC-010: Refresh cookies shall follow SRS-AUTH-020 and shall never be transmitted over plain HTTP outside localhost development.
- SRS-SEC-011: Personal-data retention and anonymization shall follow SRS-DATA-012 through SRS-DATA-015 and the approved privacy policy.
- SRS-SEC-012: Authorization shall be covered by negative tests, especially OWNER-to-OWNER isolation.

## 9. Performance and capacity requirements

The following are initial service-level objectives measured at the API process, excluding client network latency:

- SRS-PERF-001: Across API requests under the normal load profile, p95 response latency shall be less than 500 ms and p99 response latency shall be less than 1 second.
- SRS-PERF-002: Public-menu response latency shall be less than 1 second at p95 under the normal load profile.
- SRS-PERF-003: The service shall support 500 concurrent active users, 100 requests per second sustained, and bursts of 200 requests per second.
- SRS-PERF-004: Default list page size shall not exceed 20 and maximum page size shall not exceed 100 unless an endpoint specifies a stricter limit.
- SRS-PERF-005: Public list, menu filter, review list, user order list, and place order-queue queries shall use indexed predicates represented in the Prisma schema.
- SRS-PERF-006: Database transactions shall contain only required database work and shall not perform remote calls or QR image generation.
- SRS-PERF-007: Caching shall be introduced only after profiling and shall not weaken authorization or data freshness requirements.
- SRS-PERF-008: Checkout shall support 20 requests per second without duplicate orders or inconsistent order state.
- SRS-PERF-009: The representative load test shall execute: a one-minute ramp from 0 to 100 users; 100 concurrent users for 10 minutes; 500 concurrent users for 10 minutes; and a burst of 1,000 concurrent users for 1 minute.
- SRS-PERF-010: The load test shall pass only when the error rate is below 1%, API p95 latency is below 500 ms, no duplicate orders are created, and no inconsistent inventory or order state is observed.

## 10. Reliability and concurrency requirements

- SRS-REL-001: Multi-record invariants identified in `application-rules.md` shall be executed in transactions.
- SRS-REL-002: Unique-code collisions shall be handled with bounded retry rather than surfaced as an internal error.
- SRS-REL-003: Concurrent order-status updates shall produce at most one valid transition from an expected state.
- SRS-REL-004: Refresh rotation and reuse response shall remain consistent under concurrent refresh requests.
- SRS-REL-005: Scheduled expiry and audit operations shall be idempotent.
- SRS-REL-006: Application shutdown shall disconnect Prisma cleanly.
- SRS-REL-007: The production deployment shall define a database backup and tested restore process.
- SRS-REL-008: A readiness check should verify critical application configuration and database connectivity without exposing secrets.
- SRS-REL-009: The production service shall target 99.5% monthly availability, measured at the externally reachable API health boundary and excluding approved maintenance windows documented before they begin.

## 11. Logging, monitoring, and operability

- SRS-OPS-001: Winston shall provide structured application logging suitable for the deployment environment.
- SRS-OPS-002: Every request should carry or receive a correlation/request ID.
- SRS-OPS-003: Logs shall record route, method, status, duration, and safe actor/resource identifiers where available.
- SRS-OPS-004: Authentication failures, authorization denials, refresh-token reuse, unexpected server errors, and repeated verification failures shall be observable.
- SRS-OPS-005: Metrics should include request latency/error rate, checkout outcomes, order-state counts, expiry counts, and database health.
- SRS-OPS-006: Environment configuration shall be validated during startup and the process shall fail fast when required secrets or `DATABASE_URL` are absent.
- SRS-OPS-007: Production errors shall preserve diagnostic context in secure logs while returning sanitized responses.

## 12. Maintainability and quality requirements

- SRS-QLT-001: TypeScript compilation shall pass with the project's configured strictness.
- SRS-QLT-002: ESLint and Prettier checks shall pass before merge.
- SRS-QLT-003: Business decisions shall reside in services, HTTP concerns in controllers, and Prisma queries in repositories.
- SRS-QLT-004: Feature repositories shall not be exported to other modules by default.
- SRS-QLT-005: `common` and `lib` shall not depend on feature modules.
- SRS-QLT-006: New requirements shall include automated tests proportional to risk.
- SRS-QLT-007: Schema changes shall update Prisma migrations, affected API specifications, and requirement documents.

## 13. Verification strategy

### Unit verification

- Service tests shall verify role and ownership decisions, money calculations, review restoration, order transitions, and token-reuse behavior.
- Schema tests shall verify boundaries, enum values, normalization, and rejected unknown/invalid input.
- Pure helpers such as order-code generation shall be tested independently.

### Integration verification

- Repository tests shall run against PostgreSQL and verify unique constraints, soft-delete filters, ownership predicates, transaction rollback, refresh-session replacement, and order snapshots.
- Migration tests shall apply the schema to an empty database and validate required seed roles.

### End-to-end verification

- Registration, login, refresh rotation/reuse, logout, and user deactivation.
- SUPER_ADMIN user and role administration.
- ADMIN platform-operations access, including denial of SUPER_ADMIN-only role and security administration.
- Two OWNERs managing different places, including negative cross-tenant attempts.
- Two CASHIERs assigned to different places, including negative cross-place reads and status mutations.
- Public place/menu discovery and filtering.
- Verified-purchase review creation, one-review-per-order enforcement, repeat reviews from different completed orders, deletion, restoration, and moderation.
- Cart isolation, unavailable-item handling, and checkout.
- Idempotent checkout retry and concurrent status updates.
- Order-code/verification-token lookup, minimal disclosure, and OWNER-authorized processing.

### Release gate

- SRS-TST-001: Prisma schema validation and generation shall pass.
- SRS-TST-002: Build, lint, unit tests, integration tests, and critical E2E tests shall pass in CI.
- SRS-TST-003: No known critical/high authorization or secret-exposure defect may remain open for release.
- SRS-TST-004: Database migration and rollback/restore procedures shall be reviewed before production deployment.
